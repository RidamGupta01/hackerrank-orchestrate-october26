# Activity and recovery analysis

## Purpose and contract

`src/activity_analyzer.py` exposes `ActivityAnalyzer` for the State
Reconstruction Agent. It combines the global `system_activity.csv` stream,
confirmed identity relationships, the actual deletion rules, and optional
case-linked `EvidenceObservation` records. It does not produce deletion
statuses, propose final output steps, or treat activity outcomes as proof.

```python
from src.activity_analyzer import ActivityAnalyzer

analyzer = ActivityAnalyzer.from_csv(
    "dataset/system_activity.csv",
    rules_path="dataset/deletion_rules.csv",
)
report = analyzer.analyze_resolution(
    confirmed_identity_resolution,
    evidence=case_evidence_observations,
)
structured = report.to_dict()
```

`analyze_resolution` accepts only a `CONFIRMED` identity result. `analyze`
accepts the equivalent explicit identifier collection and audit timestamp.
The returned `ActivityReport` has a chronological `events` sequence and
resource-level `processes` assessments. Event records preserve `activity_id`,
timestamp, source and target systems, resource ID, result claim, temporal basis,
association basis, and corroborating file or linking activity IDs.

## Correlation and provenance

An activity row is associated with the subject only when one of these explicit
links exists:

1. An exact supplied identity value appears in the activity details using
   identifier-aware boundary matching.
2. A case-linked evidence observation contains that identity and the same
   `resource_id` as the activity.
3. A `LINK_RESOURCE_IDENTITY` activity explicitly names the identity and
   resource. This is represented as `activity_identity_link_claim`, with the
   linking `activity_id` retained; it is not upgraded to a verified identity
   relationship.

No join is inferred from event ordering, the resource prefix alone, a common
system, or a generic success status. Resource IDs and activity IDs come from
the source data and are never generated by the analyzer. Nonmatching global
activity rows are omitted from that subject's report.

## Activity interpretation

Observed event types map to structured kinds:

| Event types | Kind |
|---|---|
| `DELETE_RECORD`, `REDACT_RECORD`, `ANONYMIZE_RECORD` | Deletion / redaction / anonymization |
| `SYNC_RECORD`, `UPDATE_RECORD` | Synchronization / update |
| `CREATE_EXPORT` | Export |
| `INDEX_RECORD`, `REFRESH_CACHE` | Search indexing / cache refresh |
| `RESTORE_BACKUP` | Backup restoration operation event |
| `CHECK_RESTORE_ACCESS`, `BLOCK_RESTORE` | Restore access check / block operation |
| `CHECK_DATA_FLOW`, `DISABLE_DATA_FLOW` | Flow status check / disable operation |
| `RETAIN_RECORD`, `SEND_EMAIL`, `CLASSIFY_REQUEST` | Retention / delivery / request classification |
| `LINK_RESOURCE_IDENTITY` | Explicit identity-resource link claim |

Each row's `reported_result` is explicitly marked as a claim. Even `SUCCESS`
does not prove the requested mutation completed; `FAILED` and `PARTIAL` are
also retained as reports rather than final resource state. A
`execution_stage` describes whether the details read as an operation attempt,
a reported result, or only a logged event; it does not upgrade the status
claim.
`RESTORE_BACKUP` event is not by itself proof that restoration occurred. A
`DISABLE_DATA_FLOW` or `BLOCK_RESTORE` row is not proof the path is currently
inactive or blocked.

Event timestamps are sorted for sequence reconstruction. Events after
`audit_at` remain visible with `AFTER_AUDIT` temporal basis but cannot be used
to establish an earlier state. The analyzer does not reinterpret a historical
operation as a current process.

## Active flows and recovery paths

`ProcessAssessment.state` is the state explicitly observed in the latest
identity-linked evidence snapshot eligible by the cutoff, not a projection
from the activity status. `state_temporal_basis` distinguishes a snapshot
captured exactly at `audit_at` from a historical one. A data flow is `ACTIVE`
or `DISABLED` only when an eligible evidence observation explicitly provides
an `enabled` value. A backup path is `RESTORABLE` or `BLOCKED` only when
eligible evidence explicitly provides `restore_allowed`. Otherwise its state
is `UNKNOWN`; any latest activity statement is separately exposed as
`latest_activity_claim`, with its `activity_id`.

The `can_recreate_data` value describes the state at `audit_at`: it is `true`
or `false` only for an evidence snapshot captured exactly at the cutoff, and
`null` when unknown or when the latest evidence is merely historical.
`observed_can_recreate_data` separately records the risk at the snapshot's
observation time. Later-captured evidence is listed in
`excluded_after_audit_evidence_ids` and never used for the cutoff state. This
distinguishes a current active path from a completed historical operation,
restore risk from actual restore, and a status claim from corroborated state.

For a `BACKUP_ARCHIVE`, the analyzer reads the supplied rule rather than
assuming deletion is required. The verified rule is `rule_14`: when restore
access can be blocked, the required action is `RETAIN`. The assessment returns
the rule ID, action, and exact condition; a restorable backup is thus surfaced
as a restore risk, not automatically classified for deletion.

The observed activity taxonomy contains no dedicated backup-creation or
import event type. `CREATE_EXPORT` is present; synchronization, indexing,
cache refresh, restore, deletion, and flow-control events are present. Backup
presence and restore capability must therefore be established from the
identity-linked backup evidence records and current access-state evidence,
not by inventing an activity event.

## Fail-closed boundaries

- Later-captured or later-observed evidence cannot establish state at an
  earlier audit cutoff.
- Historical activity and activity status claims do not become current
  process states.
- Missing activity or evidence does not establish absence.
- Unknown process state remains `UNKNOWN`; it does not imply a flow is safe.
- The supplied deletion rules are read as data; this module does not invent
  policy or decide a final deletion outcome.
- Activity details and evidence text are untrusted data. The analyzer does
  not execute or follow embedded instructions.
